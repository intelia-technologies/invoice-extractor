02 — Architecture

Three-Layer Stack

All provider-specific logic lives in JSON. The engine interprets it generically. The popup orchestrates the workflow. No hardcoded provider logic anywhere.

1 Provider JSON providers/*.json
Purely declarative definitions — one JSON file per SaaS provider. Each defines the billing URL, CSS selectors for the invoice table, field extraction rules, date format, download method, and filename template. Config fields support multi-account setups with template interpolation.
20 providers billingUrl readySelector extract.rows extract.fields download.method config (multi) preNavigation orgCheck
chrome.scripting.executeScript ↓ MAIN world
2 Generic Engine engine.js
Self-contained IIFE injected into the target tab's MAIN world. Exposes window.__invoiceEngine.execute(provider, config). Runs preSteps, extracts fields from rows using CSS selectors, parses dates (9 formats including Spanish & European), handles click simulation with full pointer/mouse events for React/Radix components, intercepts window.open() for click-download, and supports select-based pagination.
preSteps simulateRealClick parseDate (9 formats) extractField window.open intercept pagination dedup
{ count, invoices } ↑ results
3 Popup Orchestrator popup.js  ~3,745 lines
The command center. Manages the full workflow lifecycle: tab creation & reuse, readySelector polling with login auto-detection, preNavigation for org/account switching, orgCheck validation, multi-config expansion (zip by index), download dispatch via chrome.downloads / chrome.debugger, persistent download history with CSV export, profiles system for saved configurations, and a floating window mode for persistent UI.
workflow engine tab management login detection preNavigation orgCheck download dispatch history + CSV profiles floating window recorder UI
03 — Download Methods

Seven Ways to Get a PDF

Every SaaS platform serves invoices differently. The engine supports 7 download methods, chosen per-provider in the JSON definition.

Method Mechanism Use Case Providers
direct-link Creates <a download> and clicks it. Popup.js downloads via chrome.downloads. Direct PDF URLs on the page Webflow, Elastic, ZeroSSL
fetch-blob fetch() with credentials: 'include', convert to blob, download. Same-origin PDFs that need cookies/auth Vultr, Vonage, GitHub
open-tabs Opens each invoice URL in a new browser tab. External invoice pages (manual save) Shortcut
print-page Opens receipt URL + triggers window.print(). Receipt pages with print-friendly layouts —
chrome-download Opens URL in background tab, listens for chrome.downloads.onCreated. Supports postLoadClick for secondary buttons. Pages with redirects, JS triggers, or download buttons OpenAI, Hetzner
debugger-print chrome.debugger attach → Page.printToPDF → base64 blob → download. Fully automated. Receipt pages with no PDF export Hover
click-download Multi-step click sequences per row. Intercepts window.open() to capture signed URLs. Popup.js downloads via chrome.downloads. Buttons that trigger server-side signed URLs or AJAX downloads Amazon, Google Cloud, Twilio, CodeRabbit
04 — Execution Flow

What Happens When You Click "Download All"

The full lifecycle from button click to downloaded PDFs, showing how popup.js orchestrates the engine across multiple providers.

Phase 1
Batch Configuration
User sets "since" date and max invoices. Active providers are expanded: multi-value config fields (e.g., 3 Google Cloud accounts) are zipped by index into separate workflow entries.
Phase 2 — Per Provider Loop
Provider Processing
Each provider is processed sequentially. Unconfigured providers are auto-skipped.
2a
PreNavigation
If configured, opens a preparatory URL (e.g., repositories page) and executes steps to switch org/account before navigating to the billing page.
2b
Open Billing Tab
Finds existing tab on the provider's domain or creates a new one. Navigates to billingUrl (with config templates resolved). Waits for tab load + 2s SPA render delay.
2c
Iframe Detection
If provider uses iframe.urlPattern, polls chrome.webNavigation.getAllFrames() for up to 30 seconds to find the matching frame.
2d
ReadySelector Polling
Polls for the readySelector CSS selector at 1-second intervals (30s timeout). Acts as login auto-detection — if the selector appears after the user logs in, download starts automatically.
2e
OrgCheck
If configured, reads the page element (e.g., breadcrumb) and compares with the expected org from config. Blocks download with a clear message if mismatched.
2f
Engine Injection & Execution
Injects engine.js into the tab's MAIN world. Engine runs the full extraction pipeline:
i. Execute preSteps (click tabs, wait for elements)
ii. Query rows via CSS selector
iii. Extract fields from each row (selector, attr, regex, template)
iv. Filter by sinceDate
v. Deduplicate by configurable field
vi. Execute download method per invoice
2g
Download Dispatch
Popup.js receives the invoice list and dispatches downloads via the appropriate mechanism (chrome.downloads, chrome.debugger, background tabs, etc.)
2h
History & Next
Downloaded invoices are saved to persistent history (with download IDs for "open in Finder"). Progress updates. Auto-advance to next provider.
Phase 3
Completion
Summary screen shows completed providers, skipped providers (with reasons), and total downloads. History is queryable and exportable as CSV.
05 — Recorder

How Providers Are Discovered

The recorder captures everything the user does on a billing page. All pattern detection happens post-hoc — the recording JSON is then fed to Claude Code for automatic provider generation.

Click Capture

  • Event listener on document (capture phase)
  • Records: tag, text, CSS selector, href, frame context
  • Dialog awareness (is click inside a modal?)
  • Download detection (checks download attr, file extensions)

DOM Snapshots

  • Initial snapshot of all tables on the page
  • Click-context snapshots (nearest container around clicks)
  • Sanitized: emails redacted, sensitive data stripped
  • Tracking URLs and analytics parameters removed

Network & Downloads

  • PerformanceObserver watching resource entries
  • Auto-detects PDF/document fetches
  • Intercepts window.open() and URL.createObjectURL()
  • Tags download method: open-tabs or fetch-blob

Dialogs & Modals

  • MutationObserver watching for [role="dialog"]
  • Detects OOPIF dialogs (empty content + child iframes)
  • Re-scans after 500ms for late-rendering content
  • Captures button inventory per dialog

Post-hoc Analysis

After recording stops, analyzeRecording() identifies patterns from the captured data:

  • Invoice table candidates — tables/lists with 2+ rows, sorted by row count. Includes interactive element inventory per row.
  • Date format detection — regex patterns ordered by specificity (DD/MM/YYYY, MMM DD YYYY, etc.)
  • Download method detection — most common method from recorded downloads
  • ReadySelector candidates — tables with data-test-id, billing containers, fallback to headings
  • Pagination candidates — native selects with year/period options, custom dropdowns, next/prev links

Output: JSON file → fed to Claude Code's /add-provider skill → automatic provider JSON generation

06 — Provider Schema

Anatomy of a Provider

Complete annotated schema showing every possible field. Each provider JSON is a full declarative specification of how to navigate, extract, and download invoices.

providers/example-provider.json 
{
  "id": "example-provider",           // kebab-case unique identifier
  "name": "Example Provider",          // display name in UI
  "icon": "📋",                          // emoji fallback (PNG icon preferred)
  "billingUrl": "https://app.example.com/billing/{{config.accountId}}",
                                          // supports {{config.*}} templates

  "readySelector": "table.invoices tbody tr",
                                          // CSS selector confirming page is loaded

  // ─── Per-user configuration ───
  "config": {
    "accountId": {
      "title": "Account ID",
      "type": "string",
      "default": "",
      "multi": true              // multiple values → N workflow entries
    }
  },

  // ─── Pre-navigation: switch org/account before billing page ───
  "preNavigation": {
    "url": "https://app.example.com/settings",
    "readySelector": "button[aria-haspopup='dialog']",
    "steps": [
      { "action": "click", "selector": "button", "wait": 1000 },
      { "action": "click", "selector": "span", "text": "{{config.org}}", "wait": 3000 }
    ]
  },

  // ─── Org/account verification ───
  "orgCheck": {
    "selector": "a[href='/']",        // element with current org name
    "configField": "org"             // config field to compare against
  },

  // ─── Cross-origin iframe support ───
  "iframe": {
    "urlPattern": "payments.example.com"  // substring match on iframe src
  },

  // ─── Extraction rules ───
  "extract": {
    "preSteps": [                      // interactions before extraction
      { "action": "click", "selector": "button[role='tab']", "text": "Invoices", "wait": 2000 },
      { "action": "waitFor", "selector": "table tbody tr", "timeout": 10000 }
    ],
    "rows": "table.invoices tbody tr",   // CSS for each invoice row
    "fields": {
      "id":          { "selector": "td:nth-child(1)" },
      "date":        { "selector": "td:nth-child(2)" },
      "amount":      { "selector": "td:nth-child(3)" },
      "downloadUrl": { "selector": "a.download", "attr": "href", "resolve": true }
    },
    "dateFormat": "auto",             // auto | M/D/YYYY | DD/MM/YYYY | MMM DD, YYYY | ...
    "dedup": "id",                    // field to deduplicate by
    "pagination": {                    // optional
      "type": "select",               // select | click-next (engine) | url-page (popup)
      "openSelector": "...",
      "optionSelector": "...",
      "wait": 2000
    }
  },

  // ─── Download configuration ───
  "download": {
    "method": "click-download",       // one of 7 methods
    "steps": [                          // for click-download: per-row click sequence
      { "selector": "button[title='Download']", "scope": "row", "wait": 2000 }
    ],
    "filenameTemplate": "{{name}}_Invoice_{{id}}_{{date}}.pdf"
  }
}
07 — Key Decisions

Why It Works This Way

Architectural decisions that shape the system. Each solves a specific problem encountered while building support for real-world billing pages.

01

No Service Worker Logic

background.js is a stub that only logs on install. All orchestration runs in popup.js via a floating window (chrome.windows.create({ type: 'popup' })). This keeps state management simple and avoids service worker lifecycle issues.

02

MAIN World Injection

The engine runs in the page's JavaScript context, not Chrome's isolated world. This is essential: React/Radix/MUI components ignore events from isolated contexts, and window.open() interception only works from the same JS realm.

03

Popup Handles Downloads

For direct-link and fetch-blob, popup.js uses chrome.downloads.download() instead of in-page mechanisms. This bypasses Chrome's "allow multiple downloads" permission prompt and ensures proper cookie/auth handling across domains.

04

Dual Execution for Iframes

When providers use cross-origin iframes, preSteps and download steps run from popup.js (not inside the engine). The iframe may detach and reload after clicks — popup.js can re-discover the frame ID, unlike engine.js running inside the destroyed frame.

05

Window.open Interception

For click-download, the engine monkey-patches window.open() before clicking download buttons. Chrome's popup blocker blocks synthetic window.open after the first call — intercepting captures the URL so popup.js can download via the extensions API.

06

Multi-Config Zip

When providers have multiple multi: true fields (e.g., email + accountId), values are paired by index, not as a cross-product. This handles the common case of N billing accounts each tied to a specific email, without producing N² combinations.

07

Recorder: Capture Everything, Analyze Later

The recorder doesn't try to identify provider patterns during recording. It captures raw data (clicks, DOM, network, downloads) and runs all analysis in analyzeRecording() after stopping. The recording JSON is then fed to Claude Code's /add-provider skill, which generates the provider JSON automatically. This separation keeps the recorder simple and the analysis reproducible.

08 — Alternatives

Why Not Something Else?

Every approach to automated invoice downloading has tradeoffs. The Chrome extension approach wins on the dimension that matters most: authentication.

Chrome Extension
(this project)
User is already logged into every SaaS. No auth management. Declarative JSON providers. Works with any billing page that renders in Chrome.
Best fit
Browser Automation
Playwright / Puppeteer
Requires a separate browser instance. Auth management nightmare — storing credentials, handling MFA, session expiry. Runs headless, can't reuse existing sessions.
Auth is the problem
API Integrations
Per-provider REST/GraphQL
Each provider needs custom API auth (OAuth, API keys). Many SaaS don't expose billing APIs at all. Doesn't scale — every provider is a custom integration.
Doesn't scale
Email Parsing
Gmail/Outlook automation
Parse invoice emails and extract PDF attachments. Incomplete coverage (not all providers email invoices), delayed delivery, format fragility across email clients.
Partial coverage
Manual Download
The status quo
Log into each SaaS, navigate to billing, download PDFs one by one. Tedious, error-prone, doesn't scale. This is what most teams do today.
Doesn't scale
